feat(ffi): foreign blocks — call C libraries with the boundary type-checked

The adoption blocker. A `foreign` block includes a header, names the
library to link, and declares signatures:

  foreign "math.h" link "m" {
      float sqrt(float x);
      float pow(float base, float exponent);
  }

The signatures are registered like any other function, so a call across
the boundary is checked rather than trusted. Passing a str where the
library takes a float is E005 at build time; the wrong number of
arguments is E002; the return type flows into the assignment and a
mismatch is E001. That is precisely what E005 — Boundary Perimeter
Contamination — has described since the taxonomy was written, and it now
does it.

No prototypes are emitted. The header already declares the functions and
re-declaring them risks conflicting with the real signature. Linked
libraries are collected and passed to the C compiler as -l flags.

`foreign` and `link` are contextual, not reserved, so neither word is
taken from user code.

One bug caught by testing the output rather than the checker: foreign
return types were not recorded for code generation, so str(sqrt(x))
routed a float through the integer converter and printed 12 instead of
12.0. Direct calls were affected while assignments through a typed
variable were not, which is the kind of gap a checker-only test misses.

examples/ffi_math.sta calls libm; five conformance tests cover the
checks. All nine suites green, fixpoint holds, conformance 84.
