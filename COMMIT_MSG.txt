feat(wasm): freestanding WebAssembly target, with measured sizes

`--target wasm` now produces a real module. Verified by building and
running one: exports ['memory','classify','label','checksum','score_of'],
classify(900) returns "PRIME", label(900) returns "tier: PRIME", and
fib(25) returns 75025. Strings and allocation work inside the module —
label concatenates through the prelude's bump allocator.

A freestanding wasm build has no libc, so compiler/runtime_preamble_wasm.c
supplies the subset the language needs: a bump allocator, strlen/strcmp/
memcpy, integer and float formatting, and the string helpers. `print` goes
through one imported host function, so a module that never prints imports
nothing. Every top-level function carries an export_name attribute,
because a wasm module has no main() to start from.

The trade-offs are in the README rather than omitted: no free, so a
long-running module exhausts its heap; no file I/O; floats format to six
decimals because shortest-round-trip needs snprintf and strtod. This
suits computation, not a server, and WebAssembly still cannot touch the
DOM — the layout tier stays server-rendered.

Measured, not estimated:

  two integer functions            136 bytes
  four string functions            595 bytes  (436 gzipped)

This replaces the "15 KB browser bundle" the README claimed before any of
it was built. The real figure is smaller, but the point is that it is now
a measurement rather than a number someone wrote down.

test_suite/wasm_target.py builds a module and checks its magic number and
exports. It needs clang with a wasm32 target, which gcc cannot provide, so
it reports a skip on machines without one and runs in CI, which has it.
Sizes are printed rather than asserted: an assertion would be either
meaningless or brittle, and this project has already published one bundle
size that nothing measured.

Ported to both implementations; all suites green and the fixpoint holds.
