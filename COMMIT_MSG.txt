feat(runtime): table persistence — save and load

Tables survived only as long as the process. `save T to "p";` and
`load T from "p";` write and read rows as tab-separated text, with
serialisers generated per table from its schema. Verified across two
runs of the same binary: the first finds nothing and writes two rows, the
second reads them back.

Text rather than a binary format, so a table is inspectable with the
tools everyone already has and readable by something that is not this
compiler. Tabs, newlines and backslashes inside string fields are
escaped, and a literal tab inside a value round-trips.

Stated in the README rather than left to be discovered: no schema
versioning, no migration, no locking, no index, no transactions. Field
order is the declaration order and that is the contract — a file written
under one schema will mis-parse under another, and two writers will
corrupt it. This is enough for one process to keep state across
restarts, and is not a database.

`save` and `load` are contextual, so neither word is taken from user
code. A save or load naming a table that was never declared is E004.

Noted while testing: a query is only parsed in declaration position, so
`len(A <- [id > 0])` does not parse and needs a binding first. Worth
fixing, but it is a parser limitation rather than a runtime one.

Conformance 97; all ten suites green; fixpoint holds.
